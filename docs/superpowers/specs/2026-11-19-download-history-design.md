# ダウンロード履歴の自動記録

## 目的と承認済みの範囲

FPSshogi-Releases の配布回数の推移を継続して確認できるようにする。ユーザーは GitHub Actions での実装を依頼し、実行周期を1日3回程度と指定した。

## 構成

- GitHub Actions を日本時間 01:17・09:17・17:17（UTC `17 0,8,16 * * *`）に実行する。時刻は実装側の選択。手動実行と実装ファイル更新時の検証・初回記録にも対応する。
- Python 3.11以降の標準ライブラリのみを使う。全ページの公開リリースから `FPSshogi-Windows.zip` の `download_count` を取得する。
- `stats/downloads/history.csv` に観測時刻、現在公開中の累計、削除済みの最後の観測値も保持した累計、前回との差、リリース数などを追記する。
- `stats/downloads/assets.csv` に各観測時点のアセットID別件数を追記し、`state.json` に前回状態を保存する。
- グラフ閲覧専用の `stats/downloads/trends.md` とSVGに累計・確認日別増加・最新版ごとの件数を表示する。ユーザーの追加指定に従い、READMEにはこの別ファイルへのリンクだけを置く。確認日別増加は観測区間の終端日に集計し、実際のダウンロード日別ではないと明記する。
- 既存READMEから履歴へのリンクを追加する。保存先は main ブランチ。外部サービスや追加の個人トークンは使用しない。

## 保存先の比較

main内の専用フォルダは管理・閲覧・通常のgit pushが最も単純で、この配布用リポジトリに適している。別ブランチは通常履歴を分けられるが同期・初期化が増える。Actions artifactsだけでは保存期限があり継続履歴に向かない。今回はmain内を採用する。

## データの扱い

- 最初の累計は基準値とし、初回の増加数を空欄にする。過去の会話の92回・121回は日別の実測データとして埋めない。
- IDが違う再アップロードは別アセットとする。削除済みIDの最終観測値は残す。記録される前に削除されたファイルの値は復元できない。
- API失敗・不正な応答・同じIDのカウンター減少・不整合な既存履歴では失敗終了し、Gitに新しい観測を保存しない。失敗を0件に置き換えない。
- 同じActions run IDの再実行は観測を重複させない。観測日時は実際の取得時刻を使い、スケジュールの時刻を実測時刻として使わない。
- リポジトリ書き込みは `contents: write` に限定し、同時実行を直列化する。保存は通常のpushのみで、競合時はrebaseして再試行する。

## 完了条件

重要な集計条件の自動テストが成功し、mainに反映されたActionsが実際に1回成功して、CSV・グラフのコミットを確認できること。
